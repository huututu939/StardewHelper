# StardewAutoPush 开发记录

PC 端 SMAPI mod：游戏一保存，自动把当前农场存档经局域网推给「星露小助手」App。
长线任务全貌见任务书（App 端 Part B 在 StardewHelper 仓库轮次内推进）。

## mod-a1 / 1.0.0（2026-11-07，骨架：配对码上传闭环）

- **范围**：GameLoop.Saved（存档写完后触发）→ 主线程只捕获存档路径/农场名 →
  Task.Run 打包 zip（内容在根、Optimal、**排除游戏备份** `_old/_SVBAK/_SVEMERG/
  SaveGameInfo/BACKUP_SAVE`，防超 App 20MB 上限）→ UDP 38217 广播「SDH-FIND」发现
  （失败回退 config.AppIp + 38217~38236 端口扫描；故意不做全网段扫描——保存路径
  上不能每次都扫 254 个连接）→ POST /upload（X-Stardew-Proto: 2 + 6 位码 +
  X-Stardew-Device-Id 前瞻头）→ 403 含「验证码」换码重试 ≤3 次。
- **线程纪律**：后台线程零 Game1 访问；HUD 文案走 ConcurrentQueue，UpdateTicked
  主线程弹出；Interlocked 防抖（上次没传完本次跳过）；异常全兜底不冒泡到 SMAPI。
- **持久化**：DeviceId 用 helper.Data 全局数据（跨 mod 更新保留）；Token 状态机留给
  mod-a2（App 端信任协议就绪后接）。
- **控制台命令**：sdh_status / sdh_push / sdh_pair（当前≡push）/ sdh_untrust（提示无可清）。
- **验证**：dotnet build 0 错误（CS9057 分析器版本差警告，无害）；ModBuildConfig
  自动部署进 E:\steam\...\Mods\StardewAutoPush。
- **验收**：2026-11-07 用户真机（游戏 1.6.15 + SMAPI 4.5.2）验收通过（原话「可以用了」）：
  睡觉保存后 HUD 三连「保存完成，正在同步存档到手机… → 请在手机上输入配对码 482823 →
  手机已收到（116 KB）」，手机端输码后走确认抽屉导入成功。

## mod-a2 / 1.1.0（2026-11-07，Token 状态机：零输码自动同步）

- **背景**：App 端 c231（信任设备协议）已装机验收——配对即导入 ✓、Token 颁发 ✓。
  用户实测确认 mod-a1 每次推送仍弹码框：App 每次都把带码请求当新配对（行为正确），
  缺的是 mod 侧不存 Token。本轮补上状态机，打通「保存 → 零手动」闭环。
- **改法**：
  ① Token 状态机：有 Token → 免码直传（X-Stardew-Device-Id/Token/Device-Name）；
     200 "imported"/"noop" = 成功；**401 = 信任被撤销/失效 → 清 Token 并在本次推送内
     直接回退配对**（不用再等一次保存）；403 含「验证码」= App 版本旧（不认识
     Token 头）→ 本次回退码流程，Token 不动（c230 及以前的 App 兼容）；
  ② 无 Token → 配对流程（6 位码 + DeviceId + 电脑名），200 "paired" 里领 Token
     持久化到 helper.Data **全局数据**（app-token），mod 更新不丢、配对只做一次；
  ③ 发现兜底：UDP 广播被手机省电窗口偶发吃掉（c231 轮实测丢过一次回应）→
     成功地址写入全局数据（last-app），UDP 哑火时按它直探，仍不做全网段扫描；
  ④ X-Stardew-Device-Name 头（电脑名清洗与 App 端 sanitizeName 同口径）；
  ⑤ 响应 JSON 用 System.Text.Json 解析（.NET 6 自带，零新依赖）；旧 App 纯文本
     响应解析不了就回退旧文案；
  ⑥ 控制台命令升级：sdh_status 显示配对状态/上次 App 地址；sdh_pair = 清 Token +
     立即重配；sdh_untrust = 清 Token。
- **验证**：dotnet build 0 错误（游戏运行中，EnableModDeploy=false 验证编译；
  关游戏后重新 build 自动部署 1.1.0 进 Mods）。
- **验收**：2026-11-07 用户真机验收通过（原话「可以了」）：最后一次输码配对后
  Token 持久化，后续推送不再弹码框、手机直接自动导入——mod 侧「保存→零手动」闭环达成。

## mod-a3 / 1.3.0（2026-11-09，快捷键 + GMCM 设置页：一键推送/一键配对）

- **背景**：用户反馈：「现在要进 mod 控制台输命令再回车才能同步。第一次配对之后虽然
  自动了，但**第一次**还是得进控制台——能不能做成快捷键，或集成进游戏设置里？」
  拆成两个诉求：① 触发方式要**游戏内随手可点/可按**；② **首次配对**也不该走控制台。
- **改法**：
  ① **快捷键**（默认 F5 = 立即推送、F6 = 重新配对）：用 SMAPI 官方 mod 按键机制
     [StardewModdingAPI.Utilities.KeybindList]（1.6 标准做法，**不自己挂 Win32 钩子**——
     那会跟游戏的键盘分发器打架）。绑定串存在 config.json（`PushKeybind`/`PairKeybind`），
     格式 "F5" / "F5,LeftShift" / "F5|F6"（多组用竖线）；
  ② **F6 = 一键重新配对**：清 Token + 立即推送，手机上弹框让你输 6 位码——
     **首次配对也彻底不用碰控制台**；
  ③ **菜单打开时不响应**：玩家可能在打字/给 NPC 取名，这时按 F5 应该是打字而不是推送
     （误触代价不对称）；标题界面/玩家对象未建好时也不响应；
  ④ **Suppress 吃掉按键**：`helper.Input.Suppress` 逐个 SButton 抑制，
     这样别的 mod 绑同一个键时不会两边都触发。⚠ KeybindList 可能有多个绑定、
     每个绑定又可能是组合键，要**摊平**成 SButton 列表逐个抑制，只抑制第一个会漏；
  ⑤ **GMCM 集成**（用户已装 spacechase0.GenericModConfigMenu）：游戏设置里出现
     「星露小助手」页签，能改两个快捷键 + 自动推送开关 + HUD 提示开关 + 手机地址。
     **用反射调 GMCM API、不引用 GMCM 程序集**——直接引用会跟 GMCM 版本硬耦合，
     它一升级换签名我们的 mod 就会在加载时崩；反射的失败模式是「少个设置页签，
     功能降级成手改 config.json」，游戏照常玩。GMCM 没装也安静降级；
  ⑥ 解析口径**只有一处**（GmcmIntegration.ToKeybindList）——GMCM 里显示的绑定和
     实际生效的绑定必须是同一个解析结果，两处各写一遍迟早漂移（改了一处没反应）；
     认不出来时返回**空列表**而非 null（GMCM 拿到 null 的 KeybindList 渲染时会 NRE，
     整个 GMCM 菜单打不开）；改键立刻落盘 + 重载绑定（不必重启游戏）。
- **控制台命令保留**：sdh_push / sdh_pair / sdh_status / sdh_untrust 一个没删——
  快捷键是**加**的，不是替掉的（有人习惯命令，也有人手抖按错键）。
- **验证**：dotnet build 0 错误；ModBuildConfig 自动部署 1.3.0 进 Mods（游戏未运行，
  没有 DLL 锁）。**真机验收待用户**（按 F5 看手机有没有收到、F6 看配对码弹没弹、
  GMCM 页签出不出来）。
- **计划中**：
  - 验收标准 1-9 全项实测扫尾 + 合规文档（App 侧致谢页注明协议来源）。

## mod-a3.1 / 1.3.1（2026-11-09，修 GMCM 初始化时机 + HUD 消息图标）

- **起因（用户实测反馈两处）**：① 按 F5/F6 都生效，但 SMAPI 控制台**爆红**：
  `Tried to access a mod-provided API before all mods were initialized.`；
  ② 游戏左下角弹消息时，文字前面有个**米黄色空方框**，用户希望把 App 图标放进去。
- **问题①根因**：mod-a3 在 `Entry()` 里就调 GMCM 的 API —— 那一刻别的 mod 还没初始化完，
  GMCM 的 API 拿不到。**修法**：改到 `SaveLoaded` 再接（SMAPI 保证所有 mod 初始化完的时点）。
  GMCM 与 HUD 图标补丁（AssetRequested）**都**挂到 SaveLoaded。
- **问题②根因（反编译确认）**：那个空方框是 [StardewValley.HUDMessage] 的**通用消息图标位**——
  它从 `LooseSprites\Cursors` 纹理的 (293, 360, 26, 24) 那一格取材，
  而那一格在原版里**本来就是空的**（给「没有具体图标的消息」当占位）。
- **问题②修法（关键设计取舍）**：
  - ⚠ **不自己算坐标画图标**：HUD 图标位置由游戏算
    （`titleSafe.Left+16, titleSafe.Bottom-112-heightUsed-64`，还跟着分辨率/UI缩放/消息条数变），
    自己复刻一份必然对不上，对不上就是「图标盖住文字」这种更糟的结果；
  - ✔ **改纹理本身**：用 SMAPI 的 `AssetRequested` 拦下 `LooseSprites/Cursors`，
    用官方 `IAssetDataForImage.PatchImage` 把我们的图标（64×64 母版，assets/sdh_icon.png）
    贴进那一格（Overlay 模式，只覆盖图标自己的像素）。之后**游戏照常画**，
    坐标/顺序/缩放全由游戏负责——我们只换「那一格是什么」，零风险；
  - ⚠ **必须主动 InvalidateCache**：游戏很早就加载过 Cursors 纹理（鼠标箭头也用它），
    缓存命中就不会触发 AssetRequested 补丁 → 补丁等于没接。接上后立刻失效缓存强制重载；
  - ⚠ **越界即放弃**：目标格不在纹理里（游戏大版本挪了位置）就什么都不做，
    宁可留个空框也绝不画歪。
- **验证**：dotnet build 0 错误；ModBuildConfig 自动部署 1.3.1 进 Mods（assets 目录一并部署，
  config.json 已含 PushKeybind/PairKeybind）。**真机验收待用户**（重启游戏看：控制台不再报红、
  弹消息时图标位是 App 图标）。
- **计划中**：
  - 验收标准 1-9 全项实测扫尾 + 合规文档（App 侧致谢页注明协议来源）。

## mod-a3.2 / 1.3.2（2026-11-09，修两条控制台红字）

- **起因（用户实测反馈）**：控制台还爆红，两条：
  ① `Tried to map a mod-provided API to class 'System.Object'; must be a public interface.`
  ② `HUD 图标加载失败…failed loading content asset 'assets/sdh_icon.png' from the game content`
- **①根因**：mod-a3 用了 `helper.ModRegistry.GetApi<object>(GmcmId)`。
  SMAPI 的**泛型** `GetApi<T>()` 要求 T 是**公开接口**，传 object 直接报错。
  **修法**：改用**非泛型** `GetApi(string)` —— 它返回 object、不做接口检查，
  正好配合反射方案（GMCM 的接口类型在不同版本里挪过位置，编译期引用不得）。
- **②根因**：`helper.GameContent.Load<Texture2D>()` 加载的是**游戏内容路径**
  （"LooseSprites/xxx"），而 `assets/sdh_icon.png` 是 **mod 自己的文件**。
  **修法**：改用 `helper.ModContent.Load<Texture2D>()`，路径相对 mod 根目录。
- **验证**：dotnet build 0 错误；部署 1.3.2 进 Mods。**真机验收**：用户反馈「控制台不爆红了」。

## mod-a3.3 / 1.3.3（2026-11-09，HUD 图标改走 messageSubject——前两版方向是错的）

- **起因（用户实测反馈）**：控制台不红了，但**图标还是不显示**。
- **根因①（低级错误）**：`e.Edit(asset => …)` 回调里拿到的 `asset` 是
  **[StardewModdingAPI.IAssetData]（接口）**，不是 Texture2D。
  我们写的是 `if (asset is not Texture2D) return;` —— 这个判断**永远为真**，
  回调**每次都提前 return**，补丁一行都没执行。
  （日志里能看到 "SaveAutoPush edited LooseSprites/Cursors.zh-CN"，
  那只说明**事件触发了**，不代表回调里真的贴了图——这是这次判断失误的地方。）
- **根因②（更关键：方向本身就错了）**：反编译 [StardewValley.HUDMessage].draw（1.6.15）看原版
  怎么画消息框，结论是那个"空方框"**根本不是图标位**，而是**气泡的左端帽**。
  原版消息框是**三段拼**的：
  ```
  左端帽   (293, 360, 26, 24)   4 倍缩放，画在 (titleSafe.Left+16, titleSafe.Bottom-112-heightUsed-64)
  拉伸中段 (319, 360,  1, 24)   横向拉到文字宽度
  右端帽   (323, 360,  6, 24)   4 倍缩放
  ```
  也就是说 (293,360,26,24) 这一格**全游戏的 HUD 消息共用**。
  ⚠ 就算把根因①的接口判断修对、把图标贴进去，也会导致
  **游戏里每一条消息**（成就、报错、收获……）的框子都变成我们的图标——
  那是污染原版 UI，而且那一格本来就不是空的（是圆角气泡的边），贴上去还会把边框弄花。
  **所以 1.3.1/1.3.2 那套「改纹理」方案从根上就是错的，必须换路子。**
- **新方案（走 messageSubject，游戏自己的绘制入口）**：
  原版代码里，框子**中间那个图标**是这么画的：
  ```csharp
  if (messageSubject == null)  按 whatType 画成就/错误/体力等内置图标;
  else                          messageSubject.drawInMenu(b, vector, …);
  ```
  所以只要把 `HUDMessage.messageSubject` 设成一个**我们自己画的 Item**，
  游戏就会在框子里把我们的图标画出来：
  - 坐标、缩放、层级、动效**全由游戏负责**——一行公式都不用抄，
    也就不会出现「图标盖住文字」或随分辨率漂移；
  - **只影响我们自己的这条消息**，原版 UI 一个像素都不碰；
  - 图标加载失败时退回普通消息（原来的空框样子），不会把消息搞没。
- **实现**：新增 [StardewAutoPush.SdhIconItem]（继承 [StardewValley.Item]）。
  ⚠ Item 是抽象类，要实现 5 个抽象成员
  （`TypeDefinitionId` / `DisplayName` / `maximumStackSize()` / `getDescription()` /
  `isPlaceable()` / `drawInMenu`），漏一个就编译不过。
  drawInMenu 照抄原版 Object 的画法：`location + (32,32)` 为原点、4 倍缩放，
  我们的母版是 64×64（4 倍尺寸），所以实际缩放再乘 0.25 → 屏幕 64×64。
  ⚠ Item 基类带 NetFields（联机同步字段），但这个 Item 只被**读**、从进背包，
  所以共用**同一个实例**即可（每次 new 都白初始化一遍字段）。
- **验证**：dotnet build 0 错误；ModBuildConfig 自动部署 1.3.3 进 Mods
  （manifest 1.3.3、assets/sdh_icon.png 一并部署）。
- **验收**：2026-11-09 用户真机验收通过（原话「验证过了，现在显示图标了」）：
  控制台无红字、F5 推送正常（HTTP 200，8 条已勾选）、HUD 消息框中间显示 App 图标。
  SMAPI 日志佐证：`SaveAutoPush 1.3.3` 加载、`HUD 图标已就绪。`、
  `Accessed mod-provided API (GenericModConfigMenu.Framework.Api)`（GMCM 页签在）、
  `HTTP 200：{"status":"imported","keys":8}`；全日志无 ERROR/WARN。
  ⚠ **原版消息框未被污染**（走 messageSubject 的关键收益）也由用户确认。
- **计划中**：
  - 验收标准 1-9 全项实测扫尾 + 合规文档（App 侧致谢页注明协议来源）。

## 收口（2026-11-09，App 侧 c235）

- **验收标准 1-9 全项扫尾**与**合规文档**已在 App 侧 c235 落地
  （见 `安装包归档/版本备注.md` 的 c235 条目）：
  - 任务书原文**不在仓库里**（当初直接发在对话里），本轮从会话存档
    （`~/.zcode/cli/db/db.sqlite` 的 message/part 表）**原样捞回**，逐条对齐，
    没有凭记忆补；
  - App 侧新增 verify 第 152 节（44 条断言），钉住 1-9 里**可静态核验**的部分：
    全局数据持久化 / 不用 WriteJsonFile / 只存令牌哈希 / imported·noop 应答 /
    自动导入复用既有落库链 / 有信任设备即自动监听 / 进行中标志与 ConcurrentQueue /
    **401 与 403 严格分离且 401 文案不含「验证码」**（不把旧 bat 带偏）/
    旧端口段·UDP 发现·SAF·Steam 路径仍在 / 线程纪律 / 合规文案。
  - 1-9 里**必须真机跑才有意义**的几项（连续存 3 次的导入计数、断网、撤销信任、
    旧 bat 回归、3 个真实存档对比）**留给用户验收**，Agent 不自己宣布「已验证」。
- **mod 侧本轮零改动**（1.3.3 保持不变），只把 verify 里的 mod 版本钉点
  1.2.0 → 1.3.3 跟上。
